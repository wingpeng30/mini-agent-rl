## Failure ledger and third-search boundary

The Q surface anchor gate in v122 B and D rejected seven proposed queries in each arm. Each arm made nine repair calls; six ended `repair_ungrounded`, leaving only 42 B and 41 D final answers. Every saved repair call saw the same visible evidence as the immediately rejected proposal; the added repair instruction changed the prompt, not the evidence. These outcomes are controller terminations, not necessarily malformed JSON or model protocol failures. The old regular expression accepted a lexical substring as a proxy for entity grounding and rejected some valid name or punctuation forms. This establishes a controller-side source of loss, but the fixed-arm result does not prove that every rejected query was semantically good. The v123 query guard therefore blocks only empty or repeated searches and records lexical overlap as an unverified diagnostic. The old v122 behavior and all original scores remain untouched. Invalid actions and real parser failures stay separate from controller rejection.

For C, the two-reviewer audit plus saved trajectories classify 29 exact answers outside the disputed group, two evidence-supported but strictly wrong answers, eight two-search answers agreed unsupported, nine disputed or uncertain reviews (including two strict matches), and two cases with fewer than two searches. This is a diagnostic partition, not a causal attribution. In particular, supported-but-wrong cases point toward answer selection or scoring review before adding a search; unsupported cases can involve a missed query, absent corpus fact, truncation, or wrong entity. The per-case record preserves multiple fault tags and the earliest observable fault; it does not force one root cause.

The CPU third-search analysis (`diagnosis/third-search-report.json` and its private per-case file) replayed any different second query found in B/D for C's unresolved cases. Five raw alternatives existed, but **none** simultaneously had an existing single API judgment of grounded query and targeting the missing relation. We did not author a query from gold answers or use a later document as earlier support. There is no recorded model-produced third query, and no v123 third-search accuracy result. On future GPU inference, compare two- versus at-most-three searches from the same fixed second-search state and evidence, keeping all other settings constant. Preset gates: net strict EM +3/50, no mean F1 drop, at least 95% retention of prior correct answers, at least 98% protocol validity, and zero unresolved answer-support disputes before any candidate promotion. This is research on the exposed development set only, not validation on the new internal set.

A separate post-hoc check against official annotated supporting sentences (`diagnosis/annotated-coverage-report.json`) finds both annotated facts in the frozen corpus for all 50 C questions. The saved searches brought all annotated facts into top-3, and those facts remained visible in the final processed input, for 34 questions. Among those 34, five answers were still strictly wrong; among the 16 without full annotated-fact coverage, 14 were wrong and two correct. This narrows the observed retrieval/answer bottlenecks but does not prove that an annotated fact is the only valid evidence or that a third query would recover it. No gold or supporting title was used to make a query.
